# ADR-018: Перевод ошибок ApiError поверх Feign

Дата: 2026-10-23. Статус: принято (лаба №2).

## Контекст

В монолите исключения контекста-поставщика ловил вызывающий контекст
in-process. В лабе №2 поставщик отвечает HTTP-ошибкой (единый формат
`ApiError` — code, detail, retryAt, traceId), а потребитель получает
`FeignException` и должен сохранить семантику (например, 409
`PLANT_NOT_ELIGIBLE` с `retryAt` при резерве).

## Решение

- Все сервисы отвечают ошибками в едином формате `ApiError`
  (`shared-lib`, ADR-017) с доменными кодами (`PLANT_NOT_ELIGIBLE`,
  `IMAGE_RESTRICTED`, `PLANT_UNDER_RESERVATION`, …).
- Потребитель декодирует `FeignException.contentUTF8()` → `ApiError`
  (`ApiErrorDecoder` в каждом сервисе с Feign-клиентами) и переводит в
  своё доменное исключение, **сохраняя код, detail и retryAt**
  поставщика; свой обработчик отдаёт их клиенту как свои (409 остаётся
  409, `retryAt` доживает до ответа).
- Недекодируемое тело (не наш формат) — общая ошибка зависимости.
- **Circuit breaker (Resilience4j) + fallback на каждом Feign-клиенте**:
  fallback бросает `DependencyUnavailableException` → 503
  `DEPENDENCY_UNAVAILABLE` («сервис временно недоступен»), а не 500.
  Конфигурация инстансов — в config-repo каждого сервиса.

## Последствия

- Коды ошибок сквозные: клиент gateway'а видит код сервиса-поставщика.
- Fallback скрывает причину (детали в логах) — сознательно: наружу
  единая 503, детали — трассировка.
- Лаба №4: тот же формат переносится на Kafka-ошибки (dead-letter +
  код).
