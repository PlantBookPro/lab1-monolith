# Ревью happy path — автоматизированный прогон API

Сквозной прогон лабы №1 через REST API с фиксацией каждого запроса и ответа.
Скрипт: [`scripts/happy-path-review.sh`](../../scripts/happy-path-review.sh),
текущий отчёт: [`2026-10-04-happy-path-review.md`](2026-10-04-happy-path-review.md).

## Что проверяет

Полный happy path (раздел 13 требований) одним прогоном:

1. **Модератор** — админ создаёт пользователя и назначает роль `moderator`.
2. **3 участника** — создаёт модератор; каждый задаёт координаты
   (обязательны для глобального турнира).
3. **Глобальный турнир — автоматом**: загрузка изображения → заявка растения →
   автоматическая ONNX-модерация scheduler'ом (без ручных ручек, ADR-009) →
   `POST /global/entries` без приглашений → `QUEUED` (ADR-012).
4. **Приватный турнир**: модератор создаёт DRAFT (тег, дедлайн, длительность
   раунда, доля выбывания), открывает регистрацию, приглашает участников;
   каждый принимает приглашение со своим растением → `READY` (резерв
   изображения, ADR-010).
5. **Старт** по дедлайну — scheduler (или идемпотентная demo-ручка `run-due`):
   `RUNNING`, участия `ACTIVE`.
6. **Раунд 1** — голосование `LIKE`/`DISLIKE`, выбывает p3 (растение `DEAD`).
7. **Раунд 2** — выбывает p2 (голосует и выбывший p3 — допущение 9),
   p1 — `WINNER`, турнир `FINISHED`.
8. **Результаты** — `GET /results`: победитель и выбывшие с раундами
   выбывания; растения выбывших `DEAD`, победителя — `ALIVE`.

Сценарий фиксированный: 3 участника, выбывают p3 затем p2, победитель p1.
Каждому участнику нужно **2 растения** с разными изображениями: пара
(owner, fingerprint) допускает только один активный резерв (допущение 4,
ADR-010) — одно изображение в глобальный турнир, другое в приватный.

## Требования

- Запущенное приложение: `docker compose up --build` (healthcheck
  `http://localhost:8080/actuator/health`).
- `curl`, `jq`, `python3`.
- Изображения: по умолчанию 6 кропов эталонной ромашки
  (`src/test/resources/moderation/reference/daisy.jpg`) генерируются
  через `sips` (macOS); на Linux — передайте готовые `p1a.jpg…p3b.jpg`
  через `IMAGES_DIR` (кропы внутри пары участника обязаны различаться).

## Запуск

```bash
./scripts/happy-path-review.sh
```

Все параметры — переменными окружения:

| Переменная | По умолчанию | Описание |
|---|---|---|
| `BASE_URL` | `http://localhost:8080/api/v1` | базовый URL API |
| `ADMIN_ID` | поиск в БД | UUID админа; иначе ищется по `ADMIN_EMAIL` |
| `ADMIN_EMAIL` | `admin@plantarena.local` | email bootstrap-админа |
| `DB_USER` / `DB_NAME` | `postgres` / `plantarena` | БД для поиска админа |
| `SRC_IMAGE` | эталонная `daisy.jpg` | JPEG-источник для 6 кропов |
| `IMAGES_DIR` | — | каталог с готовыми `p1a.jpg…p3b.jpg` |
| `OUT` | `docs/review/<дата>-happy-path-review.md` | файл отчёта |
| `DEADLINE_SECONDS` | `150` | запас до дедлайна регистрации |
| `ROUND_SECONDS` | `15` | длительность раунда голосования |
| `MODERATION_TRIES` | `20` | попыток опроса модерации (по 2 с) |

Пример — быстрый прогон с короткими раундами и своим админом:

```bash
ADMIN_ID=<uuid> ROUND_SECONDS=10 DEADLINE_SECONDS=90 \
  ./scripts/happy-path-review.sh
```

## Отчёт

Markdown-файльник: каждый шаг — блок `http` (метод, путь, заголовок
`X-Demo-User-Id`, тело) и ответ с кодом статуса и JSON. В конце — итоговая
таблица «статус / шаг / HTTP» и вердикт. Код возврата скрипта: `0` — все шаги
успешны, `1` — есть неуспешные, `2` — ошибка окружения (приложение не
поднято, нет зависимостей, админ не найден).

Дедлайны не ждём «честно»: там, где важна воспроизводимость, используется
`POST /api/v1/internal/demo/jobs/run-due` — тот же use case, что scheduler
(идемпотентен; `processed=0` означает, что scheduler уже успел сам).
