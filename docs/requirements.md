# Plant Arena — полная спецификация (исходные требования лабораторных работ)

> Скопировано дословно из согласованного ТЗ (2026-09-23). Разделы 0–17.
> Лаба №1 — разделы 0–17 в объёме итераций 0–9 (см. раздел 15); лабы №2–4 — раздел 16.

Ты — backend-разработчик и архитектор JVM-приложения Plant Arena. Спроектируй систему турниров растений и реализуй её поэтапно в рамках четырёх лабораторных работ. Сейчас нужно реализовать лабораторную №1.

Это **один Spring Boot монолит в одном Maven-модуле**. Внутри он разделён на bounded contexts по правилам Domain-Driven Design. Каждый контекст — отдельный пакет верхнего уровня с собственной моделью, схемой БД и опубликованным контрактом. Границы проверяются автоматическими архитектурными тестами, а не структурой сборки. Цель — чтобы в лабе №2 любой контекст можно было перенести в отдельный сервис копированием его пакета и заменой адаптеров, без переписывания доменной модели и use cases.

Разработка ведётся по **TDD**: сначала падающий тест, затем минимальная реализация, затем рефакторинг. Тесты являются исполняемой спецификацией правил из этого документа. Порядок работы и требования к тестам описаны в разделе 14.

### 0. Принципы, которые важнее любых частных указаний ниже

1. **Единый язык (ubiquitous language).** Названия классов, методов, событий, таблиц, эндпоинтов и тестов берутся из глоссария (раздел 4.1). Если в ходе работы появляется новое понятие, сначала дополни глоссарий, затем пиши код.
2. **Богатая доменная модель.** Правила и переходы состояний живут в агрегатах, value objects и доменных сервисах, а не в application-сервисах и не в контроллерах. Анемичные сущности с сеттерами и логикой «снаружи» не допускаются.
3. **Домен не знает об инфраструктуре.** Пакеты `domain` не зависят от Spring, JPA, Jackson, HTTP, Kafka и других контекстов.
4. **Граница контекста — граница будущего сервиса.** Между контекстами — только UUID, опубликованные контракты (`api`) и события. Никаких JPA-связей, общих Entity, общих репозиториев и JOIN в чужие таблицы.
5. **Сначала тест.** Ни одного правила из разделов 3–9 без теста, который его формулирует. Покрытие — следствие, а не цель.
6. **Один Maven-модуль.** Не создавай multi-module build, отдельные артефакты `-api`/`-domain`/`bootstrap`. Изоляцию обеспечивают пакеты, ArchUnit и дисциплина зависимостей.

### 1. Границы задачи

Приложение — смесь социальной сети и турниров, но социальная функциональность в текущем объёме ограничена профилями, лентой растений, голосованием, приглашениями и результатами. Не добавляй друзей, подписки, комментарии, чаты и отдельный frontend. Swagger UI — единственный интерактивный интерфейс. Загрузка изображений, создание пользователей и турниров, принятие приглашений, голосование и просмотр результатов должны быть доступны через него.

Пользователь загружает фотографию растения. Фотография проходит автоматическую проверку наличия растения. Одобренное растение может участвовать в турнире. Лайк даёт +1, дизлайк −1. Согласно правилам турнира участники выбывают, их растения погибают; остаётся победитель. Кроме отдельных закрытых турниров существует постоянный глобальный турнир с географическим отбором и непрерывным финалом.

Не путай учётную запись, изображение, экземпляр растения и участие в турнире — это разные понятия единого языка, принадлежащие разным контекстам. Не храни турнирный счёт в профиле пользователя или непосредственно в изображении.

### 2. Роли и создание пользователей

| Действие | Гость | USER | MODERATOR | ADMIN |
|---|---|---|---|---|
| Смотреть глобальную ленту и лидерборд | Да | Да | Да | Да |
| Голосовать в глобальном турнире | Да | Да | Да | Да |
| Загружать собственные растения, участвовать в турнирах | Нет | Да | Да | Да |
| Смотреть закрытый турнир | Нет | Если приглашён/участвует | Свой турнир или приглашение/участие | Да |
| Голосовать в закрытом турнире | Нет | Если подтвердил участие и был допущен к старту | Только если сам участник | Только если сам участник |
| Создавать обычных пользователей | Нет | Нет | Да | Да |
| Создавать и управлять турнирами | Нет | Нет | Своими | Любыми |
| Назначать/снимать роль MODERATOR | Нет | Нет | Нет | Да |

MODERATOR и ADMIN сохраняют пользовательские возможности. Администратор не может голосовать в чужом закрытом турнире только на основании своей роли. Организатор не получает автоматического права голоса и не становится участником автоматически.

Публичной самостоятельной регистрации нет. Модератор создаёт учётную запись USER; затем этот пользователь заполняет профиль и загружает растение для глобального турнира. Аккаунт существует и без одобренной картинки, но в турнир до одобрения не попадает. Первый ADMIN создаётся отдельным bootstrap-механизмом из переменных окружения; повторный запуск не создаёт дубликат. Модератор не может передать роли в DTO создания пользователя или повысить права через PATCH профиля.

**Лаба №1:** бизнес-проверки выполняются через `CurrentActor` и `AccessPolicy`. `CurrentActor` (userId, роли, признак гостя) — технический тип в `shared.security`; его провайдер реализует контекст identity. Каждый контекст имеет **свою** `AccessPolicy` с правилами своего языка (например, «участник, допущенный к старту» — понятие tournaments, а не identity). В профилях `dev` и `test` разрешён `X-Demo-User-Id`: пользователь и его роли извлекаются из БД, роли из заголовка не принимаются. Отсутствие заголовка означает гостя, неизвестный/неактивный ID — ошибку. Это механизм демонстрации, **не настоящая аутентификация**. Документируй его в Swagger. В остальных профилях он отключён; до появления JWT запуск обычного профиля без адаптера идентификации должен завершаться явной ошибкой конфигурации.

**Лаба №3:** заменить только адаптер провайдера `CurrentActor` на Spring Security + JWT в `Authorization: Bearer ...`; удалить возможность использовать demo-заголовок вне тестов. Доменные правила и `AccessPolicy` не меняются — это должно подтверждаться тем, что их тесты остаются без изменений. Пароль разрешён во входном DTO создания учётной записи и входа, но никогда не присутствует в ответах, списках, логах и Entity-сериализации. Хранить только хэш уже с лабы №1, например через `PasswordEncoder` из `spring-security-crypto` (за доменным портом `PasswordHasher`). Секреты в учебных сценариях передавать через окружение, реальные пароли не коммитить.

### 3. Предлагаемые продуктовые решения

Следующие положения уточняют неоднозначности исходной идеи. Запиши их в ADR как **предлагаемые допущения**, а не как уже согласованные с преподавателем требования. Используй их для непротиворечивой реализации по умолчанию. Каждое допущение должно иметь хотя бы один тест, названный в терминах единого языка.

1. **Гибель относится к экземпляру растения.** Погибший `Plant` никогда не воскресает. Допустимая повторная загрузка создаёт новый экземпляр с новым ID.
2. **После поражения в закрытом турнире изображение запрещено навсегда; после поражения в глобальном — на 24 часа.** Суточное правило является исключением глобального режима. Постоянный запрет имеет приоритет над временным.
3. **Область запрета — пара `(ownerId, imageFingerprint)`.** Чужое поражение не блокирует фотографию у всех пользователей. Глобальный запрет для всех владельцев и поиск украденных фото — отдельная политика, сейчас не реализуются.
4. **Одно и то же изображение одного владельца не участвует одновременно в нескольких турнирах.** Резервирование начинается при подаче заявки, включая очередь глобального турнира, и заканчивается отказом/отменой/завершением. Это предотвращает ситуацию, когда растение погибло в одном турнире, но продолжает жить в другом. Для закрытого турнира можно загрузить другую картинку. Победитель закрытого турнира освобождается для повторного участия. Одновременное участие одной картинки потребовало бы другой явно согласованной модели распространения гибели.
5. **Одно активное глобальное участие на пользователя.** После гибели можно сразу подать другое изображение; суточный запрет касается только совпавшей картинки, а не всей учётной записи.
6. **Самоголосование запрещено для идентифицированного пользователя.** Гость определяется анонимной сессией, поэтому без авторизации невозможно гарантировать уникальность физического человека или исключить обход через новую сессию. Не обещай абсолютную защиту от накрутки.
7. **Голосование привязано к окну/раунду.** Один голос одного субъекта за одного участника в одном окне. Голос можно поменять или удалить до закрытия окна. Новое окно допускает новый голос; счёт окна начинается с нуля.
8. **Ничья разрешается детерминированно:** score DESC, joinedAt ASC, entryId ASC. При отсутствии голосов действует тот же порядок. Выбор tie-break документируется как учебное правило.
9. **Выбывший участник закрытого турнира может продолжать голосовать до его завершения.** Право получают участники, допущенные к старту, а не просто приглашённые пользователи. Снявшийся до старта такого права не получает.
10. **Модерация может завершиться после дедлайна, но не даёт задним числом права участия.** К старту закрытого турнира изображение должно быть APPROVED, заявка подтверждена и резервирование завершено. Неуспевшая заявка не допускается, приглашение истекает. Изображение остаётся доступным для другого турнира после освобождения резерва.

### 4. Стратегическое проектирование (DDD)

Первым артефактом работы, до кода, являются `docs/domain/glossary.md`, `docs/domain/context-map.md` и ADR с допущениями из раздела 3. Код и тесты должны им соответствовать; при расхождении сначала правится документ.

#### 4.2. Bounded contexts

| Контекст | Ответственность и данные | Целевой сервис |
|---|---|---|
| identity | Пользователи, роли, профили, координаты, credential hash, провайдер CurrentActor | user-access-service |
| media | Метаданные файлов, отпечатки, порт `FileStorage` и локальный адаптер | file-service в лабе №4 |
| plants | Plant, запреты изображений, резервирования, правила гибели | plant-service |
| moderation | Задания распознавания, попытки, результаты, адаптер модели | plant-filtration-service |
| tournaments | Турниры, приглашения, entries, окна/раунды, голоса, authoritative score, результаты, гостевые сессии, глобальная оркестрация | tournament-service |
| geo | Политика кластеризации, версии, snapshots состава | clustering-service |
| feed | Компоновка ленты и её публичное API через read-порты | feed-service / модуль tournament-service |

Уведомления и anti-doping в лабе №1 — выходные порты и минимальные адаптеры/политики, без искусственных пустых контекстов. В целевой системе это notification-service и anti-doping-service.

**Счёт, голоса и закрытие окна принадлежат tournaments.** Не выделяй контекст подсчёта, который параллельно обновляет тот же score. Лента выбирает, что показать; право на голос и изменение счёта проверяет tournaments. Anti-doping может дать решение/сигнал, но не пишет в таблицы голосов.

#### 4.3. Context map и допустимые зависимости

Зависимости между контекстами ациклические. Контекст может использовать **только пакет `api`** другого контекста и только из своих адаптеров.

| Контекст | Может обращаться к `api` контекстов | Тип отношения |
|---|---|---|
| identity | — | Upstream для всех; Open Host Service (CurrentActor, публичный профиль) |
| media | — | Upstream для plants, moderation, feed |
| geo | — | Upstream для tournaments; получает координаты во входной команде, сам identity не читает |
| plants | media | Customer–Supplier; ACL над `MediaAsset` |
| moderation | plants, media | Downstream: подписан на `PlantSubmitted`, отдаёт решение командой в plants.api |
| tournaments | identity, plants, geo | Downstream; ACL `PlantEligibility`, `ParticipantDirectory`, `ClusteringGateway` |
| feed | tournaments, plants, media, identity | Downstream, только чтение через read-порты |

Правила, устраняющие циклы:

- plants не знает о moderation и tournaments. Когда создан `Plant`, plants публикует событие `PlantSubmitted`; moderation создаёт задание, подписавшись на него. Решение moderation передаёт командой `plants.api.PlantModeration.recordDecision(...)`.
- plants публикует `PlantModerationDecided` (APPROVED/REJECTED); tournaments подписан на него и переводит заявку (READY / возврат в INVITED).
- tournaments сообщает о гибели командой `plants.api.PlantLifecycle.registerDeath(...)`, а не записью в таблицы plants.
- Потребитель владеет своим портом (Consumer-driven): например, `tournaments.application.port.out.PlantEligibility` с собственными типами ответа; адаптер `tournaments.adapter.out.plants.InProcessPlantEligibility` вызывает `plants.api` и переводит его DTO в модель tournaments (Anti-Corruption Layer). В лабе №2 меняется только этот адаптер.

Зафиксируй context map диаграммой (C4 Container/Component или PlantUML) и таблицей взаимодействий: инициатор, получатель, команда/событие/запрос, синхронность, что будет в лабе №2 и №4.

### 5. Тактическое проектирование: агрегаты, инварианты, события

Предложенные границы агрегатов — отправная точка; окончательный выбор и отступления зафиксируй в ADR. Для каждого агрегата в `docs/domain/aggregates.md` перечисли корень, состав, инварианты, команды, доменные события и то, какой тест защищает каждый инвариант.

| Контекст | Агрегат (корень) | Ключевые инварианты |
|---|---|---|
| identity | `User` (роли, профиль, координаты, хэш пароля, статус) | USER всегда присутствует; роли меняются только отдельными командами; координаты в допустимых диапазонах |
| media | `MediaAsset` | Неизменяем после создания |
| plants | `Plant` | Переходы модерации и жизни; DEAD необратим; asset не меняется после подачи |
| plants | `ImageRestriction` | PERMANENT без expiresAt; COOLDOWN активен при `now < expiresAt` |
| plants | `PlantReservation` | Не более одного активного резерва на (ownerId, fingerprint) — set-инвариант, обеспечивается частичным UNIQUE-индексом PostgreSQL, домен лишь формулирует правило |
| moderation | `ModerationJob` | Ошибка распознавателя не является решением; устаревший результат не применяется |
| tournaments | `Tournament` | State machine DRAFT → REGISTRATION_OPEN → RUNNING → FINISHED / CANCELLED; параметры и их допустимые изменения |
| tournaments | `Invitation` | Переходы статусов, дедлайн, уникальность (tournamentId, userId) |
| tournaments | `TournamentEntry` | State machine для PRIVATE и GLOBAL |
| tournaments | `VotingWindow` (+ `WindowParticipant`, `Vote`) | `[opensAt, closesAt)`; состав зафиксирован; score = сумма текущих голосов; повторное закрытие не меняет результатов |
| tournaments | `GlobalCompetition`, `QualificationEpoch` | GLOBAL никогда не FINISHED; порядок обработки одновременных границ |
| tournaments | `GuestSession` | Хранится только хэш токена; срок действия |
| geo | `ClusterSnapshot` | Состав и версия политики неизменны после фиксации эпохи |

Доменные сервисы и политики (чистый Java): `EliminationAlgorithm` (стратегия; реализация `RoundElimination`), `ParticipantRanking` (tie-break), `ClusteringPolicy` (geohash), `ImageReusePolicy`, `FeedOrdering` (псевдослучайный ключ).

Требования к тактической модели:

- Value objects для понятий с правилами: `PlantId`, `UserId`-подобные типизированные ID внутри контекста, `ImageFingerprint`, `GeoPoint`, `EliminationFraction`, `VoteValue`, `VotingSubject`, `TimeWindow`, `Score`. Валидация в конструкторе/фабрике; некорректный объект невозможно создать. Не создавай VO ради VO для полей без правил.
- Типизированные ID не пересекают границу контекста: в `api` передаются UUID.
- Время всегда из внедрённого `java.time.Clock` (UTC); домен получает `Instant now` аргументом, а не вызывает `Instant.now()`.
- Агрегат изменяется только через методы корня, выражающие намерение (`invitation.accept(plantRef, now)`, `window.close(now, ranking)`), и возвращает/накапливает доменные события.
- Репозиторий — по одному на агрегат, интерфейс в `domain`, реализация в `adapter.out.persistence`.
- JPA-модель отделена от доменной и может содержать связи внутри контекста, не совпадающие с границами агрегатов (например, `@OneToMany` tournament → invitation для требований лабы), но репозиторий агрегата загружает и сохраняет только свой агрегат. Маппинг явный.

**Доменные и интеграционные события.** Внутренние доменные события живут в `domain`. Опубликованные события для других контекстов (`PlantSubmitted`, `PlantModerationDecided`, `PlantDied`, `InvitationCreated`, `TournamentStarted`, `EntryEliminated`, `TournamentFinished`) — в `<context>.api.event`, это published language. Уже сейчас они имеют поля будущего конверта: eventId, eventType, schemaVersion, aggregateId, aggregateVersion, occurredAt, correlationId, payload.

### 6. Изображения, модерация и запрет повторного использования

`MediaAsset` — загруженный неизменяемый файл: ID, владелец, storageKey, фактический MIME, размер, размеры изображения, rawSha256, imageFingerprint, fingerprintVersion, дата загрузки. Не храни байты в PostgreSQL и не возвращай внутренние пути хранилища.

Для лабы №1 достаточно локального файлового хранилища на Docker volume за портом `FileStorage`. Лаба №4 заменяет адаптер на отдельный file-service с S3-совместимым хранилищем.

Форматы первого этапа: JPEG и PNG, до 10 MiB, не более 20 миллионов пикселей после декодирования. Проверяй фактическое содержимое, а не только расширение/MIME клиента. Ограничение размеров проверяй до выделения больших буферов (по заголовку изображения). Файлы нельзя перезаписывать: повторная загрузка создаёт новый asset.

`rawSha256` выявляет одинаковые байты. `imageFingerprint` вычисляй по нормализованному декодированному представлению: версия алгоритма, ширина, высота, фиксированный порядок каналов, фиксированная обработка ориентации/цвета/прозрачности. Зафиксируй алгоритм и тестовые примеры (набор эталонных файлов в `src/test/resources` с ожидаемыми отпечатками). Отпечаток должен игнорировать метаданные при одинаковых нормализованных пикселях. Изменение JPEG-сжатия, ресайз, обрезка и визуально похожие картинки могут иметь другой fingerprint: perceptual matching не требуется. Не выдавай криптографический хэш за распознавание одного и того же растения на разных фотографиях.

`Plant`: ownerId, assetId, fingerprint, title, moderationStatus, lifeStatus, createdAt, diedAt, version. `moderationStatus`: PENDING / APPROVED / REJECTED. `lifeStatus`: ALIVE / DEAD. Отклонение модерацией не является гибелью и не создаёт суточный запрет. Переотправка — новая заявка с новым asset и новым Plant; старое решение сохраняется для истории. После подачи картинки в турнир заменять asset у этого Plant нельзя.

`ModerationJob`: plantId, assetId, status, attempts, nextAttemptAt, modelVersion, confidence, reasonCode, startedAt, completedAt. Ошибка распознавателя — технический retry, а не REJECTED и не APPROVED. Результат устаревшей/заменённой заявки не должен одобрить новую картинку.

Порт `PlantClassifier` возвращает результат распознавания содержимого. Основной адаптер должен действительно проверять изображение, например через выбранную предобученную модель с зафиксированной версией и порогом. Конкретную модель выбери и опиши в ADR; наличие порта без работающего адаптера не считается выполненной автоматической модерацией. Допустим HTTP inference-сервис как инфраструктура, бизнес-приложение при этом остаётся монолитом. Детерминированный тестовый адаптер разрешён только в test/demo-профиле. Проверка имени файла, MIME или случайный boolean не заменяют распознавание растения. Если модель недоступна, честно укажи незавершённость сценария; система сохраняет PENDING и повторяет проверку.

`ImageRestriction`: ownerId, fingerprint, kind PERMANENT / COOLDOWN, expiresAt, reason, sourceEntryId. Для PERMANENT expiresAt отсутствует; COOLDOWN блокирует, пока `now < expiresAt`, и разрешает при `now >= expiresAt`. Историю гибели не удалять при удалении профиля/картинки из обычного пользовательского интерфейса.

Опубликованный контракт plants `PlantEligibility` (в `plants.api`) разделяет две операции: `reserveSubmission` проверяет владельца, ALIVE, отсутствие запрета и допустимый статус PENDING/APPROVED, затем резервирует картинку; `confirmEligibility` допускает к старту только APPROVED и подтверждает существующий резерв. Поэтому незавершённая модерация допускает подачу заявки, но не участие в голосовании. Проверки и изменение резерва атомарны внутри plants. `PlantReservation` хранит ID команды/заявки (idempotency key) для идемпотентного повтора: повтор с тем же ключом возвращает тот же reservationId. Проверки только на уровне Java недостаточно: нужен частичный уникальный индекс/блокировка в PostgreSQL. Глобальный `POST /global/entries` в первой версии принимает только уже APPROVED растения.

### 7. Закрытый турнир

`Tournament`: id, creatorId, name, description, type PRIVATE, status, algorithm, registrationDeadline, roundDuration, eliminationFraction, minParticipants, createdAt, version. В лабораторной реализуй один алгоритм `ROUND_ELIMINATION`; стратегия `EliminationAlgorithm` позволяет добавлять другие без большого switch по всему коду.

Состояния: DRAFT → REGISTRATION_OPEN → RUNNING → FINISHED. DRAFT и REGISTRATION_OPEN можно перевести в CANCELLED. Удалять физически можно только черновик без истории; остальное — явная отмена или архивирование. Отмена активного турнира в первом варианте запрещена: 409. Не добавляй произвольный PATCH состояния.

Модератор создаёт черновик, задаёт даты и алгоритм, добавляет приглашения, открывает приём заявок. Принимать приглашения можно только в REGISTRATION_OPEN. Приглашать и отзывать ещё не принятые приглашения можно до дедлайна. Пользователь принимает приглашение с `plantId`; если модерация ещё идёт, сохраняется ACCEPTED_PENDING_MODERATION, но это не допуск к голосованию. После APPROVED система переводит заявку в READY, если дедлайн не прошёл и резерв ещё действителен. После REJECTED заявка возвращается в INVITED с сохранением истории последней подачи; резерв освобождается, до дедлайна можно повторить принятие с новым plantId. Терминальные REVOKED/EXPIRED и заявки отменённого турнира не меняются от позднего результата модерации.

`Invitation`: tournamentId, userId, invitedBy, status INVITED / ACCEPTED_PENDING_MODERATION / READY / DECLINED / REVOKED / EXPIRED, invitedAt, respondedAt, submittedPlantId, reservationId. Уникальность `(tournamentId, userId)`. После старта состав неизменяем. Отзыв уже принятой заявки организатором для первого варианта — 409.

При наступлении deadline scheduler вызывает тот же use case старта, что и ручка. Старт возможен при now >= deadline с числом READY-заявок не меньше minParticipants, где minParticipants >= 2. Принимать заявки разрешено только при now < deadline. Если участников меньше minParticipants, турнир автоматически CANCELLED с причиной INSUFFICIENT_PARTICIPANTS; растения не погибают, резервы освобождаются.

При старте создаются `TournamentEntry` для допущенных участников и первый `VotingWindow` (раунд). В каждом раунде `n > 1` выбывает `min(n - 1, max(1, floor(n * eliminationFraction)))` худших участников. Допустимая доля: `0 < eliminationFraction < 1`. Если остаётся один, он WINNER, турнир FINISHED; иначе начинается новый раунд с нулевыми очками. Проигравшие становятся ELIMINATED, растения — DEAD, их изображения получают постоянный запрет. Победитель остаётся ALIVE, резерв освобождается. История результатов не удаляется.

### 8. Постоянный глобальный турнир

Это один `GlobalCompetition`, который никогда не получает FINISHED. Внутри существуют конечные окна голосования и географические отборы. Не моделируй глобальный режим бесконечным private-турниром без правил переходов.

Для первой реализации используй **географическую сетку с фиксированной точностью** за `ClusteringPolicy`, например geohash выбранной длины. Это воспроизводимая учебная аппроксимация: близкие точки по разные стороны границы ячейки могут попасть в разные группы. K-means/DBSCAN не обязательны. Точность сетки задаётся конфигурацией и фиксируется в версии политики.

Пользователь хранит координаты в профиле. Проверяй latitude ∈ [−90, 90], longitude ∈ [−180, 180]. Для глобального участия координаты обязательны; наружу публикуется идентификатор/обобщённое описание кластера, а не точное местоположение. Обновление геопозиции применяется к следующему отбору и не перемещает участника посреди текущего окна.

Алгоритм:

1. Одобренная заявка попадает в очередь; картинка резервируется. Новые заявки включаются в следующую qualification epoch, а не в уже идущее голосование.
2. Например, раз в 24 часа открывается следующая эпоха. Длительность настраивается, в demo может быть несколько минут. При открытии фиксируются состав участников, clusterId и версия кластеризации. Состав кластеров меняется между эпохами.
3. В каждой непустой ячейке проводится квалификационное окно. Счёт начинается с нуля. На закрытии top-1 проходит в финал, остальные выбывают, растения погибают, совпавшая картинка блокируется этому владельцу на 24 часа.
4. Единственный участник ячейки проходит в финал при закрытии окна без голосов. Это осознанное правило первой версии.
5. Победитель отбора покидает qualification и становится FINAL_PENDING. Он не занимает одновременно место в локальном отборе и в финале. Его замена в кластере определяется в следующей эпохе.
6. Глобальный финал также работает окнами. Новые финалисты присоединяются при открытии следующего финального окна вместе с выжившими предыдущего; состав текущего окна зафиксирован. Для одновременных границ времени явный порядок: закрыть квалификацию, закрыть старый финал, открыть следующий финал, открыть следующую квалификацию.
7. На закрытии финального окна из `n >= 2` участников выбывает `max(1, floor(n / 2))` худших. При `n = 1` участник остаётся лидером. При `n = 0` финал ждёт заявок. Единственного постоянного победителя нет.
8. Проигравшие финала погибают с тем же 24-часовым запретом. Выжившие переходят в следующее окно с нулевыми очками. Их итог прошлого окна сохраняется.
9. Лидерборд всегда содержит scope, windowId, closesAt и asOf. Отдельно запрашиваются текущий финал и конкретная квалификационная группа. Не смешивай очки разных окон и кластеров.

Для всех окон время берётся из внедрённого `Clock` в UTC. Интервал полуоткрытый `[opensAt, closesAt)`: в `closesAt` новый голос уже запрещён. Остановка и рестарт приложения не должны терять окна и повторно убивать растения; scheduler (`adapter.in.jobs`) выбирает просроченные задания из БД и вызывает идемпотентные use cases.

### 9. Голоса и лента

`VotingSubject` — либо USER с userId, либо GUEST с серверным анонимным токеном. `POST /api/v1/guest-sessions` создаёт случайный непрогнозируемый токен; в Swagger его можно передавать через `X-Guest-Token`. Храни хэш токена, срок действия и лимиты. Клиент не может назначить себе произвольный субъект. Для авторизованного пользователя используй USER даже при переданном гостевом токене. Гость имеет право на +1 и −1 только в глобальных окнах.

`Vote`: id, windowId, entryId, subjectKey, value, createdAt, updatedAt. `value` — enum LIKE / DISLIKE в строковой колонке; числовой вклад +1 / −1. Уникальность `(windowId, entryId, subjectKey)`. Окно и entry должны действительно соответствовать друг другу.

`PUT .../vote` устанавливает текущее значение. Повтор LIKE после LIKE не меняет счёт, LIKE → DISLIKE даёт дельту −2, DISLIKE → LIKE — +2. `DELETE .../vote` удаляет текущий голос и компенсирует его вклад; повтор удаления безопасен. Score хранится у участника окна, может быть отрицательным, тип BIGINT. Инвариант: score равен сумме текущих голосов этого окна и entry. Вычисление дельты — чистая доменная функция с исчерпывающими unit-тестами.

Лента зарегистрированного пользователя смешивает доступные ему карточки из глобального турнира и закрытых турниров, где он был допущен к старту. Предлагай только активные открытые окна, живые допущенные растения, чужие entry и ещё не оценённые этим субъектом карточки. Карточка содержит windowId, tournamentId/scope, entryId, plantId, title, image URL, closesAt и минимальные публичные сведения о владельце. Не возвращай приватный профиль, email и точные координаты.

Случайность реализуй воспроизводимой псевдослучайной сортировкой от server-issued seed и стабильного ID. Cursor (value object `FeedCursor`) связывает seed, snapshotCutoff, lastSortKey, lastId, субъект и фильтры; защищён от подмены (HMAC). Не используй OFFSET поверх нового `ORDER BY random()` на каждой странице. Новые участники после snapshotCutoff появляются после обновления ленты. Голосование/закрытие окна может убирать карточки между запросами, но не должно повторять уже пройденный ключ. Любая выдача повторно фильтруется по правам; cursor не даёт права на чужую ленту.

Для учебного набора можно вычислять псевдослучайный ключ в SQL и документировать стоимость сортировки. Не загружай всю таблицу в память. Feed не читает чужие таблицы напрямую: он использует read-порты, реализованные через `api` владельцев, либо собственную проекцию (read model), которую обновляют опубликованные события. Выбор зафиксируй в ADR.

Лента возвращает `{items, nextCursor, hasNext}` без total; запрашивай `limit + 1`, отдавай максимум limit. По умолчанию 20, максимум 50. Невалидный cursor — 400, истёкший — 410 с предложением начать новую ленту.

Минимальная защита от накрутки: лимиты выдачи гостевых сессий и голосов, 429 с Retry-After, один голос на ключ, запрет самоголосования известного пользователя, журнал подозрительных действий за портом `AbuseSignals`. IP — дополнительный сигнал, не идентификатор человека. Полноценный anti-doping-service — будущая работа.

│   ├── security/                 CurrentActor, CurrentActorProvider (интерфейс)

Не обязательно создавать пустые пакеты. `shared` не содержит доменных понятий: никаких общих `User`, `Plant`, `Tournament`, общих ID-типов предметной области и общих Entity.

#### 10.2. Правила зависимостей (проверяются ArchUnit, тесты пишутся первыми)

1. Пакеты контекстов верхнего уровня не образуют циклов (`slices().matching("com.plantarena.(*)..").should().beFreeOfCycles()`).
2. Класс контекста A может импортировать из контекста B только `B.api..`, и только из `A.adapter..` (ACL-адаптеры и подписчики событий). `A.domain` и `A.application` не импортируют другие контексты вообще.
3. Допустимые направления — только из таблицы context map (раздел 4.3). Отдельный тест на каждое запрещённое направление.
4. Слои внутри контекста: `domain` ← `application` ← `adapter`; `api` не зависит от `domain` и `adapter` своего контекста (реализация фасада живёт в `application`).
5. `domain` не зависит от `org.springframework..`, `jakarta.persistence..`, `com.fasterxml..`, `java.net.http..`.
6. JPA-сущности (`@Entity`) и Spring Data репозитории — только в `adapter.out.persistence` своего контекста и не используются за его пределами.
7. Controllers не обращаются к репозиториям и доменным объектам напрямую — только к входным портам application.
8. `shared` не зависит ни от одного контекста.
9. `config` — единственное место, знающее о нескольких контекстах сразу (для связывания бинов).

Циклические зависимости бинов не лечить `@Lazy` или `allow-circular-references`; они означают ошибку context map. Дополнительно можно использовать Spring Modulith (`ApplicationModules.verify()` и документирование модулей), если его версия совместима с выбранным Spring Boot; ArchUnit-правила выше обязательны в любом случае. Выбор зафиксируй в ADR.

#### 10.3. Взаимодействие контекстов в лабе №1

Межконтекстные вызовы выполняются в памяти. Не добавляй Feign, Eureka, Config Server, Gateway или Kafka до соответствующих лабораторных.

- **Синхронный запрос/команда:** порт потребителя → ACL-адаптер → фасад `api` поставщика. Фасад поставщика принимает и возвращает только DTO `api`.
- **Событие:** application-слой публикует опубликованные события через порт `IntegrationEventPublisher` (in-process реализация на `ApplicationEventPublisher`). Подписчики в `adapter.in.events`.
- **Обязательные последствия** (заявка → READY после одобрения, гибель растений при закрытии окна) выполняются синхронно в той же транзакции: либо координирующим use case через порты, либо синхронным `@EventListener` в той же транзакции. Для каждого взаимодействия выбери один способ и зафиксируй в context map. `@TransactionalEventListener(AFTER_COMMIT)` и `@Async` — только для необязательных побочных эффектов (уведомления, журнал), никогда для инвариантов.
- Межконтекстная ACID-транзакция допустима в монолите только для явно перечисленных процессов (раздел 12). Такие процессы уже сейчас моделируются как явные state machines с idempotency key и reservationId, чтобы в лабе №2 заменить только адаптеры и добавить компенсацию.

### 11. Сущности, связи и ограничения БД

Все идентификаторы — UUID; время — `Instant`/UTC и PostgreSQL `timestamptz`. Enum — VARCHAR + CHECK, JPA `EnumType.STRING`, никогда ORDINAL. У конкурентно изменяемых агрегатов есть `version` (optimistic locking). Имена таблиц не конфликтуют с зарезервированными словами (`app_user`, а не `user`).

**Одна PostgreSQL, отдельная схема на контекст:** `identity`, `media`, `plants`, `moderation`, `tournaments`, `geo` (и `feed`, если у него собственная проекция). Межсхемных FK нет; ссылочная целостность между контекстами проверяется use cases и аудитом ссылок — это компромисс ради выделения сервисов, его нужно показать на ER-диаграмме.

**Миграции Flyway по контекстам.** Предпочтительно: у каждого контекста свой каталог `db/migration/<context>` и своя `flyway_schema_history` в своей схеме (несколько Flyway-бинов в `config`), чтобы при выделении сервиса его миграции переносились без переименования. Допустимый упрощённый вариант: один Flyway с каталогами по контекстам и общей сквозной нумерацией. Flyway — единственный источник структуры; Hibernate `ddl-auto=validate`, create/update в обычном запуске запрещены.

| Схема-владелец | Основные таблицы и поля |
|---|---|
| identity | app_user(id, email_normalized UNIQUE, display_name, password_hash, status, latitude, longitude, version); role(id, code UNIQUE); user_role(user_id, role_id) |
| media | media_asset(id, owner_id, storage_key UNIQUE, mime_type, byte_size, width, height, raw_sha256, image_fingerprint, fingerprint_version, created_at) |
| plants | plant(id, owner_id, asset_id, fingerprint, title, moderation_status, life_status, died_at, version); image_restriction; plant_reservation |
| moderation | moderation_job(id, plant_id, asset_id, status, attempts, next_attempt_at, model_version, confidence, reason_code) |
| tournaments | tournament; invitation; tournament_entry(id, tournament_id, user_id, plant_id, reservation_id, status, joined_at); qualification_epoch; voting_window(id, scope, tournament_id?, epoch_id?, cluster_id?, sequence, status, opens_at, closes_at); window_participant(id, window_id, entry_id, score, result, joined_at); vote; guest_session; tournament_tag; tag |
| geo | cluster_snapshot(id, epoch_id, cluster_key, policy_version); cluster_member(snapshot_id, user_id, entry_id, location_version) |
| feed | проекция карточек (см. ADR-002) |

`GlobalCompetition` можно хранить как единственную запись tournament типа GLOBAL, но ограничения приватного режима зависят от типа: у GLOBAL нет общего FINISHED и общего registrationDeadline. Qualification epoch хранится явно, чтобы восстановить временные границы и состав после рестарта.

Состояния entry: для PRIVATE — ACTIVE → ELIMINATED/WINNER; для GLOBAL — QUEUED → QUALIFYING → FINAL_PENDING → FINALIST → ELIMINATED, плюс WITHDRAWN только из QUEUED. Переход QUALIFYING → ELIMINATED также допустим. FINALIST, переживший окно, остаётся FINALIST и получает новый window_participant. Активные global-статусы для уникального индекса: QUEUED, QUALIFYING, FINAL_PENDING, FINALIST. Статус окна: OPEN/CLOSED; результат window_participant: ACTIVE, SURVIVED, ELIMINATED, PROMOTED или WINNER согласно scope. Закрытие окна фиксирует результат каждого участника, не переписывая историю прошлых окон.

Применение результата модерации надёжно завершает и решение по Plant, и переход связанной заявки: в одной транзакции фиксируются DONE у job, решение в plants и переход invitation в tournaments. Не ставь DONE до обязательного обновления заявки. При выделении сервисов эта связь заменяется повторяемой доставкой сообщения/команды.

В invitation и tournament_entry ссылки userId, plantId, assetId — логические UUID. Не делай вид, что такие UUID являются `@ManyToOne`.

Физические связи для обязательных требований лабораторной (все внутри одной схемы-владельца):

| Требование | Связь | Реализация |
|---|---|---|
| Many-to-Many без дополнительных полей | app_user ↔ role; tournament ↔ tag (фильтр по тематике растения) | Join table с PK по двум FK; `@ManyToMany` в JPA-модели |
| One-to-Many / Many-to-One | tournament → invitation; tournament → tournament_entry; voting_window → window_participant | `@OneToMany` / `@ManyToOne`, LAZY, FK |
| Many-to-Many с дополнительными полями | voting_window ↔ tournament_entry через window_participant | Отдельная Entity с двумя `@ManyToOne`, score, result, joined_at; UNIQUE(window_id, entry_id) |

Не добавляй таблицу только ради галочки без объяснения её назначения.

Ключевые ограничения: один invite на пользователя/турнир; один entry пользователя в private-турнире; один активный global entry пользователя (partial unique index по активным статусам, не вечный UNIQUE(user_id, tournament_id)); один window_participant на окно/entry; один vote на окно/entry/subject; один активный image reservation (partial unique index); opens_at < closes_at; валидные координаты; валидные значения статусов. Новое глобальное участие после поражения должно работать.

Vote лучше ссылать FK на window_participant и хранить subject_key; если window_id и entry_id дублируются, согласованность обеспечь составным FK. Индексы: deadline/status турнира, closes_at/status окна, status/next_attempt_at заданий, owner_id/created_at растений, user_id/status приглашений, window_id/score для рейтинга, fingerprint.

### 12. Транзакции и конкуренция

По умолчанию DDD-правило: **одна транзакция изменяет один агрегат**. Отступления допустимы только для перечисленных процессов; каждый описан в ADR с пометкой «работает только в монолите» и планом для лабы №2 (saga/компенсация) и №4 (outbox/inbox). Транзакционные границы задаются в application-слое, не в домене и не в контроллерах.

Реализуй и обоснуй минимум две **сложных HTTP-операции** с транзакциями:

1. **Голосование** (внутри tournaments, один агрегат `VotingWindow`): проверка доступа и открытого окна, создание/изменение vote, применение дельты score. Порядок блокировок: окно → window_participant → vote. Допустима `SELECT ... FOR UPDATE` блокировка окна с сериализацией его голосов; явно укажи ограничение throughput. Close-window берёт ту же блокировку, после чего новые голоса не проходят. Проверку времени выполняй после получения блокировки. Unique constraint защищает от дубликатов независимо от предварительного SELECT.
2. **Принятие приглашения** (межконтекстный процесс: `Invitation` + `PlantReservation`): проверка пользователя, дедлайна и статуса; резервирование изображения с idempotency key; обновление invitation — атомарно в монолите. Ошибка на любом шаге откатывает резерв. В лабе №2 это saga с reservationId, состояниями RESERVING/READY и компенсацией release.
3. **Закрытие окна/раунда** (межконтекстный процесс): зафиксировать окно и итоговый рейтинг, отметить выбывание, зарегистрировать гибель и запреты (команды в plants.api), освободить резервы, создать следующий раунд или победителя. Блокировки растений брать в устойчивом порядке по ID. Повтор close по `(windowId, sequence)` ничего не начисляет и не убивает повторно. В лабе №2/4 закрытие фиксируется локально, а гибель доставляется надёжной командой/событием с повтором.

Не держи DB-транзакцию во время загрузки файла, ML inference или длительного HTTP. Файл сначала сохраняется, затем короткая транзакция регистрирует метаданные; сбой компенсируется удалением сиротского файла/периодической уборкой. Модерация: короткая транзакция захвата задания, вычисление вне транзакции, короткая транзакция применения результата с проверкой версии.

Для межсервисных событий лабы №4 — transactional outbox + consumer inbox/дедупликация. Падение между commit и публикацией должно иметь определённый путь восстановления.

### 13. REST API

Базовый префикс `/api/v1`. `U` — текущий пользователь; `M` — модератор; `A` — администратор. Владелец ресурса проверяется отдельно от роли (в `AccessPolicy` контекста). В Swagger опиши все DTO, ограничения, enum, заголовки, примеры ошибок, multipart и порядок сценариев. Контроллер каждого контекста живёт в `<context>.adapter.in.web`; Swagger-теги соответствуют контекстам.

Общие правила: создание — 201 + Location; чтение/изменение с телом — 200; удаление без тела — 204; асинхронная операция — 202 + URL статуса. 400 — формат/валидация, 401 — отсутствующая/невалидная идентификация для защищённой ручки, 403 — нет права, 404 — ресурс не найден/скрыт политикой приватности, 409 — конфликт состояния/дубликат/запрет картинки, 413 — размер файла, 415 — формат, 429 — лимит, 503 — временная недоступность обязательной зависимости. Не подменяй ошибки кодом 200 или 500.

Доменные исключения выражены на едином языке (`ImageRestrictedException`, `RegistrationClosedException` и т. п.) и не знают об HTTP. `@RestControllerAdvice` переводит их в ProblemDetail-подобное тело `{type,title,status,detail,instance,code,fieldErrors,traceId}`. Для временного запрета картинки добавляй `retryAt`. Не раскрывай stack trace, SQL, секреты и storage keys. Коды бизнес-ошибок стабильны, текст понятен человеку.

#### Пагинация и документация

Все коллекции, включая invitations, entries, rounds, tags, результаты и лидерборды, ограничены 50 записями. Не прячь тысячи дочерних объектов внутри GET одного турнира. `size/limit` по умолчанию 20, диапазон 1–50; вне диапазона → 400. Page начинается с нуля, отрицательная страница → 400, sort — только из allowlist, всегда с tie-break по ID.

Page-списки возвращают массив/DTO items плюс `X-Total-Count` с количеством доступных записей после фильтрации; count не учитывает скрытые турниры. `/feed` — Slice/keyset без COUNT и total. Оба контракта продемонстрированы тестами и Swagger.

Одна Swagger UI-точка входа и одна OpenAPI-спецификация в монолите. Для микросервисов — Swagger UI через Gateway, агрегирующий спецификации сервисов с уникальными operationId и корректными external server URLs; отдельно уточнить, требует ли преподаватель один merged JSON или допускает выбор спецификации в общей UI (для буквального «общего Swagger» предпочтителен объединённый документ). Try it out должен работать через Gateway, а не обращаться к внутренним Docker hostname. Уникальность operationId обеспечь уже сейчас (префикс контекста).

### 14. TDD: порядок работы и тесты

#### 14.1. Цикл

Каждая функциональность разрабатывается двойным циклом:

1. **Внешний цикл — приёмочный тест use case.** Сценарий Given/When/Then из этого документа записывается как тест через HTTP (MockMvc или RestAssured) на реальном PostgreSQL (Testcontainers). Он красный.
2. **Внутренний цикл — red → green → refactor** на уровне домена и application: тест правила → минимальная реализация → рефакторинг с зелёными тестами. Затем адаптеры persistence/web.
3. Приёмочный тест становится зелёным; финальный рефакторинг, обновление глоссария и Swagger.

Продакшен-код пишется только для того, чтобы прошёл падающий тест. Если правило из разделов 3–9 не выражено тестом, оно не реализовано. Тесты называются на едином языке (`@DisplayName` на русском допустим): «погибшее растение нельзя подать повторно», «LIKE → DISLIKE меняет счёт на −2».

#### 14.2. Пирамида тестов

| Уровень | Что проверяет | Инструменты | Ограничения |
|---|---|---|---|
| Архитектурные | Правила раздела 10.2, context map, слои | ArchUnit (JUnit 5) | Пишутся в итерации 0, до предметного кода |
| Доменные unit | Агрегаты, VO, state machines, алгоритм выбывания, tie-break, дельты голосов, запреты, geohash, отпечатки, cursor | JUnit 5, AssertJ | Без Spring и без моков доменных объектов; фиксированный `Clock`/`Instant`; параметризованные тесты для границ (`n`, доли, `now == closesAt`) |
| Application | Use cases, оркестрация, идемпотентность, права | JUnit 5 + in-memory fake-репозитории | Фейки портов вместо тотального Mockito; Mockito допустим для внешних портов (classifier, notification) |
| Контрактные тесты репозиториев | Фейк и JPA-адаптер ведут себя одинаково | Абстрактный тестовый класс, наследники для fake и для JPA+Testcontainers | Гарантирует честность фейков из application-тестов |
| Адаптеры persistence | Маппинг, Flyway, ограничения и индексы БД, блокировки | `@DataJpaTest` + Testcontainers PostgreSQL | Не H2 |
| Приёмочные / API | Сценарии через HTTP, коды ошибок, приватность, пагинация, `X-Total-Count`, keyset | Spring Boot Test + MockMvc/RestAssured + Testcontainers | Время через подменяемый `Clock`-бин |
| Конкурентные | Одновременные голоса, двойное принятие, гонка голоса и закрытия, повторное закрытие | Реальный PostgreSQL, несколько потоков, `CountDownLatch` | Проверять инварианты БД, а не только отсутствие исключений |

Дополнительно:

- Test Data Builders / Object Mothers для агрегатов на едином языке (`aPlant().approved().ownedBy(alice)`).
- Singleton Testcontainers-контейнер на весь прогон интеграционных тестов.
- Для `PlantClassifier` в тестах — детерминированный адаптер; отдельный тест (тег `inference`, запускается в Compose/по флагу) демонстрирует, что основной адаптер распознаёт положительное и отрицательное изображение. Качество модели двумя примерами не доказывается.
- Опционально: мутационное тестирование PIT для `domain`-пакетов как дополнительное подтверждение качества тестов.

#### 14.3. Сборка тестов и покрытие (один модуль)

- Surefire — unit, архитектурные и application-тесты (`*Test`); Failsafe — интеграционные (`*IT`).
- JaCoCo: `prepare-agent` для обоих плагинов, `merge` двух exec-файлов, `report` и `check` по объединённым данным. Совокупный LINE coverage **не менее 70%**, сборка падает ниже порога.
- Не исключай контроллеры, сервисы и правила ради процента; допустимы только исключения генерируемого кода с объяснением.
- `./mvnw verify` — единственная команда, запускающая всё: тесты, ArchUnit, покрытие.

#### 14.4. Git и TDD

Работа по веткам `feat/...`, `fix/...`, `test/...`, `docs/...`, `refactor/...`; Conventional Commits, небольшие тематические изменения. TDD должен быть виден по истории: коммиты фичи содержат тесты вместе с реализацией или раньше неё; рефакторинг отдельными `refactor:`-коммитами. Красные тесты в `main` не попадают. При существующем репозитории не переписывай чужие изменения и историю. Не делай push/merge в удалённый main без отдельной команды пользователя. В README объясни workflow и команды проверок.

### 15. Порядок реализации лабы №1 (вертикальные срезы)

Каждая итерация начинается с тестов и заканчивается зелёным `./mvnw verify`.

0. **Скелет:** Maven Wrapper, один модуль, пакеты контекстов, ArchUnit-правила, Testcontainers, Flyway по схемам, ProblemDetail, `Clock`-бин, Docker Compose, CI-команда. Глоссарий, context map, ADR с допущениями.
1. **identity:** bootstrap ADMIN, создание USER модератором, роли, профиль, координаты, `CurrentActor` через `X-Demo-User-Id`, ошибка конфигурации без адаптера.
2. **media:** загрузка, валидация формата и размеров, отпечаток с эталонными примерами, локальный `FileStorage`.
3. **plants:** Plant, запреты, резервы с idempotency key, `PlantEligibility`, гибель.
4. **moderation:** задания, retry, реальный classifier-адаптер + тестовый, применение решения, событие в tournaments.
5. **tournaments (private):** state machine турнира, приглашения, принятие/отклонение, старт по дедлайну и вручную, отмена при нехватке участников.
6. **Голосование и закрытие раундов:** окна, голоса, дельты, блокировки, выбывание, победитель, конкурентные тесты.
7. **Глобальный турнир и geo:** эпохи, кластеры, квалификация, финал, порядок одновременных границ, рестарт без повторной гибели.
8. **feed и гостевые сессии:** keyset-лента с подписанным cursor, лимиты, 429.
9. **Готовность:** покрытие, Swagger-сценарии, README, ER-диаграмма, демонстрация inference.

### 16. Переход между лабораторными

| Этап | Что реализовать | Что сохраняется |
|---|---|---|
| №1 | Модульный монолит в одном Maven-модуле, PostgreSQL со схемами по контекстам, Flyway, REST, DTO/Entity validation, Swagger, Docker Compose, JUnit/Testcontainers/ArchUnit, покрытие ≥70% | Контексты, агрегаты, порты, сценарии, API |
| №2 | Выделение сервисов, Eureka, Config Server, Spring Cloud Gateway, OpenFeign, Circuit Breaker; отдельное владение БД | `domain` и `application` без изменений; in-process адаптеры заменяются сетевыми |
| №3 | Spring Security + JWT, реальные проверки ролей/владения | `CurrentActor`/`AccessPolicy` и бизнес-правила из №1 |
| №4 | Kafka минимум 3 брокера, несколько topics, replication; события и уведомления; file-service | Контракты `api`, IDs и state machines; меняются адаптеры |

**Процедура выделения контекста в сервис** (опиши в README как доказательство готовности архитектуры):

1. Создать новый Spring Boot проект и перенести пакет `<context>` целиком, а также нужные части `shared`.
2. Перенести схему и каталог миграций контекста без изменений.
3. `api`-фасады превратить в REST-контроллеры (или оставить контроллеры `adapter.in.web`) — DTO уже являются контрактом.
4. У потребителей заменить `adapter.out.<context>` in-process на Feign-адаптер с тем же портом.
5. Синхронные подписки на события заменить идемпотентными HTTP-командами с retry jobs (лаба №2) или outbox → Kafka → inbox (лаба №4).
6. Доменные и application-тесты переносятся без изменений и остаются зелёными. Меняются только тесты адаптеров.

**Лаба №2:** не обязательно сразу запускать все сервисы. Минимальная декомпозиция: user-access, plant, tournament и clustering; moderation пока внутри plant-service, feed — внутри tournament-service. Обоснуй дальнейшее выделение по ответственности. Каждый сервис владеет своей БД/схемой и своим пользователем БД; один PostgreSQL instance допустим для Compose, но без общего пользователя с правом писать всё.

Реактивные требования №2:

- clustering-service: Reactor + WebFlux + Spring Data R2DBC; настоящие reactive repositories, без блокирующего JDBC на event loop.
- plant-service: Reactor + WebFlux + Spring Data JPA. JPA остаётся блокирующим; синхронный транзакционный use case вызывается через `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())`, транзакция открывается внутри вызванного Spring-proxied сервиса. `Mono.just(repository.save(...))` и блокирующий Feign в event loop недопустимы. Сервис гибридный, а не полностью неблокирующий.
- tournament-service можно оставить Spring MVC + JPA.

Благодаря разделению `domain`/`application`/`adapter` реактивность добавляется только во входных адаптерах; домен не переписывается.

OpenFeign — для синхронных межсервисных запросов с timeout; в WebFlux блокирующий Feign изолировать. Circuit Breaker — Spring Cloud CircuitBreaker с Resilience4j. При недоступности plant-service fallback не может объявить растение одобренным; возвращай временную ошибку либо сохраняй pending-состояние. Повтор команд — только с идемпотентным ключом. Не ставь legacy Hystrix автоматически; если преподаватель требует именно его, сначала обсуди совместимость.

До Kafka в №2 используй долговечные состояния процессов + идемпотентные HTTP-команды и retry jobs для saga; несколько `@Transactional` методов разных сервисов не дают общей транзакции. При аварии после резерва в plant-service, но до подтверждения в tournament-service, повтор узнаёт тот же reservationId; уборка pending/компенсация освобождает orphan-резерв. После локального ELIMINATED участник немедленно исключён из голоса/ленты, даже если команда гибели ещё доставляется. Старый резерв остаётся до подтверждения гибели.

**Лаба №4:** Kafka из трёх брокеров в Compose, topics с replication.factor=3 и min.insync.replicas=2, producer acks=all и idempotence; значения проверяются в кластере, а не только записаны в README. Topics, например `plant.moderation.v1`, `tournament.lifecycle.v1`, `plant.lifecycle.v1`, `notification.requests.v1`, плюс retry/DLQ. Точные настройки сверить с выбранной версией Kafka.

События: `PlantSubmitted`, `PlantApproved`, `PlantRejected`, `InvitationCreated`, `TournamentStarted`, `EntryEliminated`, `PlantDied`, `TournamentFinished` — те же опубликованные события `api`, что и в лабе №1. Partition key — по агрегату; порядок гарантируется только внутри partition, consumers учитывают aggregateVersion. Exactly-once для Kafka + чужой БД не обещать; бизнес-идемпотентность через outbox/inbox и UNIQUE(eventId).

Уведомления минимум для приглашения, результата модерации и выбывания/победы. notification-service сохраняет уведомления, пользователь читает их REST-ручкой через общий Swagger. Email/SMS/WebSocket не обязательны.

### 17. Стек и критерии готовности лабораторной №1

Стек: Java 21, Maven Wrapper (один модуль), Spring Boot, Spring MVC, Spring Data JPA, PostgreSQL, Flyway, Jakarta Bean Validation, springdoc-openapi, JUnit Jupiter, AssertJ, Testcontainers, JaCoCo, ArchUnit; опционально Spring Modulith и PIT. Kotlin/Gradle возможны, если команда выбирает их до генерации проекта; не смешивать стеки без причины.

Перед генерацией проверь по официальным источникам совместимость стабильных release-версий Spring Boot, Java, springdoc, Testcontainers, ArchUnit, (Spring Modulith) и будущего Spring Cloud. Закрепи версии в pom/BOM/wrapper/Docker images, без SNAPSHOT, milestone, dynamic ranges и `latest`. Предпочитай BOM вместо пиннинга каждой транзитивной библиотеки. Не утверждай «самая новая версия» без проверки.

Bean Validation — на request DTO и JPA entities; доменные инварианты проверяются в домене при операциях и не дублируются аннотациями в доменных классах.

Docker Compose запускает app, PostgreSQL и, при выбранном варианте, инфраструктуру распознавания. Локальные файлы — volume. Все параметры через ENV: DB, storage, режим classifier, интервалы, ограничение upload, demo profile, bootstrap admin. `.env.example` содержит только примеры. Healthchecks, зависимость от готовности БД, retry старта и миграции позволяют `docker compose up --build` из чистого состояния. Multi-stage Dockerfile; локальный Maven не обязателен.

Лабораторная №1 готова, когда:

- `./mvnw verify` зелёный: unit, application, контрактные, интеграционные, приёмочные, конкурентные и ArchUnit-тесты проходят; объединённое LINE coverage ≥ 70% реально измерено и проверено gate-ом, а не заявлено;
- ArchUnit подтверждает отсутствие циклов и запрещённых межконтекстных зависимостей;
- каждое допущение из раздела 3 и каждый инвариант из `aggregates.md` покрыт именованным тестом;
- `docker compose up --build` поднимает систему из чистого состояния, все сценарии выполнимы через Swagger UI;
- основной inference-адаптер продемонстрирован на положительном и отрицательном изображении (или честно помечен как незавершённый);
- в `docs/` есть глоссарий, context map, описание агрегатов, ADR, ER-диаграмма со схемами по контекстам и процедура выделения сервиса.
