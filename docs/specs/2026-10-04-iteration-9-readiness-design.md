# Дизайн итерации 9: готовность (финал лабы №1)

Дата: 2026-10-04. Статус: предложен. Источник: `docs/requirements.md`
(разделы 3, 13, 14.3, 15, 17), `docs/plans/2026-09-23-roadmap.md`
(итерация 9), `docs/assignment-lab1.md`.

Итерация не добавляет функциональность: она закрывает критерии готовности
раздела 17. Новый продакшен-код — только если аудит найдёт непокрытые
правила (тесты) или реальные замечания рефакторинга.

## Решения

1. **ER-диаграмма — Mermaid `erDiagram`, отдельный файл
   `docs/domain/er-diagram.md`.** Одна диаграмма на схему-контекст
   (`identity`, `media`, `plants`, `moderation`, `tournaments`, `geo`,
   `feed`): таблицы с ключевыми колонками, типами и ограничениями
   (UNIQUE, partial UNIQUE, CHECK). Физические FK — только внутри своей
   схемы (раздел 11: tournament → invitation, voting_window →
   window_participant, vote → window_participant, cluster_member →
   cluster_snapshot). Межсхемные ссылки (owner_id, plant_id, asset_id,
   user_id, window_id из feed и т. п.) — логические UUID-связи без FK:
   компромисс ради выделения сервисов, на диаграмме выделяются явно
   (комментарий/стиль), ссылочная целостность — use cases и аудит ссылок.
   Mermaid выбран как уже используемый в `context-map.md` формат,
   рендерящийся на GitHub. Источник истины — миграции Flyway
   (`src/main/resources/db/migration/<context>`); диаграмма — снимок,
   при расхождении сначала правится миграция/документация вместе.

2. **Swagger-сценарии демо — `docs/demo/scenarios.md`.** Пошаговый
   порядок демонстрации всех сценариев через Swagger UI (раздел 13:
   «порядок сценариев»), от чистого `docker compose up --build`:
   (0) запуск и bootstrap-админ; (1) identity — создание USER модератором,
   профиль, координаты, роли; (2) media — загрузка JPEG/PNG, лимиты;
   (3) plants — подача, статусы, запреты; (4) модерация — одобрение
   (ONNX), повторная загрузка после отклонения; (5) закрытый турнир —
   черновик, теги, приглашения, приём, старт по дедлайну, отмена при
   нехватке; (6) голосование — дельты, my-vote, закрытие раунда,
   выбывание, победитель; (7) глобальный турнир — координаты, заявка,
   эпохи, кластеры, квалификация, финал, лидерборды; (8) лента и гости —
   guest-сессия, keyset-курсор, голос гостя, 429. Каждый шаг: ручка,
   заголовки (`X-Demo-User-Id`, `X-Guest-Token`), тело, ожидаемый ответ.
   Демо-ручка `POST /api/v1/internal/demo/jobs/run-due` — для продвижения
   дедлайнов вместо ожидания реального времени. Из README — раздел
   «Демо-сценарии» со ссылкой.

3. **Аудит покрытия правил — таблица соответствия.** Для каждого
   допущения раздела 3 (1–10) и каждого инварианта из
   `docs/domain/aggregates.md` — именованный тест (unit/application/
   контрактный/приёмочный/конкурентный), найденный в `src/test`. Результат
   фиксируется в `docs/domain/aggregates.md` (колонка/ссылки «какой тест
   защищает» уже предполагается разделом 5) и в плане итерации. Пробелы
   закрываются новыми тестами в этой итерации (TDD-цикл только здесь).
   Ожидание: пробелов нет или единицы — покрытие LINE ~95%, итерации 1–8
   писались по правилу «сначала тест».

4. **Точечный рефакторинг — аудит, не кампания.** Проверяются: TODO/FIXME
   в `src/main`, предупреждения компилятора (`-Xlint:all` уже в pom или
   включается), дубликаты в main-коде, файлы >400 строк без причины.
   Чинится только найденное, отдельными `refactor:`-коммитами, каждый —
   зелёный `./mvnw verify`. Переименования публичных контрактов и
   разбиение агрегатов не выполняются: риск регрессии в финальной
   итерации не оправдан.

5. **Финальная верификация раздела 17.** (а) `./mvnw verify` — зелёный,
   gate JaCoCo LINE ≥ 70% реально срабатывает (временная проверка порога
   не коммитится); (б) `./mvnw verify -P inference` — ONNX-адаптер
   демонстрирует положительное и отрицательное изображение (тег
   `inference`); (в) `docker compose down -v && docker compose up --build`
   из чистого состояния — healthcheck, миграции, smoke-прогон первых
   шагов демо-сценариев через Swagger UI (создание пользователя, загрузка
   файла, подача растения, одобрение); (г) ArchUnit — уже в verify.
   Результаты — в README (раздел «Проверка» дополняется чеклистом
   готовности).

6. **Docs-замыкание.** README: ссылка на демо-сценарии, чеклист критериев
   раздела 17. Дорожная карта: итерация 9 отмечена выполненной. Глоссарий
   новых понятий не вводит. ADR не добавляются (решений архитектуры нет);
   ADR-007/009 упоминают эталонные примеры inference — сверить
   актуальность.

## Объём изменений

- Новые файлы: `docs/domain/er-diagram.md`, `docs/demo/scenarios.md`,
  при пробелах аудита — тесты в `src/test`.
- Изменения: `README.md`, `docs/plans/2026-09-23-roadmap.md`,
  `docs/domain/aggregates.md` (ссылки на тесты), точечные `refactor:`
  правки main-кода по результатам аудита.
- Миграции, REST-контракты, домен — без изменений (кроме возможных
  точечных refactor-правок без смены поведения).

  выделения сервиса, демо-сценарии).
